# Polyglot Upgrade Report (2026-09-15)

This report covers an evidence-based review of whether Golden Boy should
become a Python + TypeScript + Rust polyglot project, per the brief's own
constraint: only add a language where it provides a *measured* benefit, and
never fabricate a benchmark or "supports X" claim. See `ARCHITECTURE_AUDIT.md`
for the full audit this report summarizes; this document is the
Section-27-style final report the brief asks for.

**Verdict up front:** no language was added. The scoped work was: formalize
the existing protocol boundary, close a previously-open benchmarking gap,
build a real workload/policy validation harness, and record what was found
— including one genuine, unflattering accuracy finding unrelated to
language choice. See §8 for the full production-readiness call.

## 1. Before architecture

Python core (`goldenboy/`, 3,566 lines, zero required runtime deps) +
`sdk/typescript` (a thin client that spawns the real CLI, 374 lines, zero
runtime deps) + a hand-maintained, hand-synced protocol
(`goldenboy/protocol.py` ↔ `sdk/typescript/src/types.ts`). 186 Python tests,
14 TypeScript tests, all passing. `docs/LANGUAGE_STRATEGY.md` already
documented why Rust wasn't in use, with benchmarks from 2026-09-13.

## 2. After architecture

**Structurally identical.** Same Python core, same thin TypeScript client,
same "no server, no database, no second implementation" shape. What's new:

- `schemas/decision.schema.json` — the protocol formalized as an actual
  JSON Schema, checked against both language implementations.
- `benchmarks/results/` — a results directory with two new, dated,
  reproducible reports (scaling, policy validation), generated by two new
  scripts (`scripts/benchmark_scaling.py`, `scripts/validate_policy.py`).
- 16 new Python tests (`tests/test_protocol_schema.py` +
  `tests/schema_support.py`, a dependency-free JSON Schema subset
  validator written for this rather than adding a `jsonschema` dependency
  — see its module docstring), 7 new TypeScript tests
  (`sdk/typescript/test/schema.test.ts`).
- `ARCHITECTURE_AUDIT.md` (this review's full findings) and this report.
- `ROADMAP.md`/`BENCHMARKS.md`/`docs/PROTOCOL.md` updated to point at all
  of the above; no existing line in any of them was reversed or
  contradicted.

No production code in `goldenboy/` or `sdk/typescript/src/` changed. No
runtime dependency was added to either package.

## 3. Why each language exists (unchanged, re-justified)

- **Python** — 100% of decision logic (budget/risk/estimation/
  classification/policy). Deterministic, typed, zero runtime dependencies,
  and — per the fresh benchmarks below — not a bottleneck at any measured
  scale except one extreme edge case (§5).
- **TypeScript** — a thin client (`sdk/typescript`) for JS/TS-based agents
  to consume the same decisions Python callers get, over a versioned
  protocol, without a second implementation of any business logic. This is
  exactly the role a polyglot upgrade would otherwise introduce from
  scratch; it already existed and is now additionally schema-checked.
- **Rust** — not used. No operation in this codebase is measurably
  CPU-bound at realistic scale (§5). The brief's own gate ("CPU bottleneck
  actually exists, Python optimization insufficient, Rust's win is
  measured, maintenance cost is reasonable") is not met for any component
  today.

## 6. Benchmark methodology

`time.perf_counter()` wall-clock timing, single process, single machine
(Apple Silicon, macOS, Python 3.13.7), no other load controlled for —
identical methodology to the existing `BENCHMARKS.md`, extended with
mean/median/p95/p99/throughput (`scripts/benchmark_scaling.py`'s own
percentile implementation, since no new dependency was added for this
either). Not a substitute for profiling under real concurrent load; treated
throughout as an order-of-magnitude signal, per this project's existing
convention.

## 7. Accuracy / validation results

`scripts/validate_policy.py` ran `DecisionEngine.decide()` for 8
representative task descriptions (small bug fix through a repo-wide
architecture change) across the brief's own 80/50/30/15/10/5% budget
curve — 48 real decisions (full table:
`benchmarks/results/2026-09-15-policy-validation.md`). Findings:

- **Classification:** 8/8 scenario prompts classified as their intended,
  non-UNKNOWN task type.
- **Policy comparison:** `GoldenBoyPolicy` (the real `RiskEngine`) is the
  only baseline in `goldenboy.core.policies` that responds to *both*
  budget and estimated cost jointly. `usage_only_safety_margin` proceeds
  at every budget level down to 5% regardless of cost (by design — it
  ignores cost entirely); `complexity_only_50pct` stops at every budget
  level once cost crosses its fixed threshold (by design — it ignores
  budget entirely). Golden Boy's real engine is the only one that shifts
  from `proceed` to `stop` exactly where the cost-to-usable-budget ratio
  crosses `caution_ratio`, at every scenario.
- **A real accuracy finding, unrelated to language choice:** all 8
  scenarios — from a one-line typo fix to a full data-model migration —
  produced the *same* ~66.4-66.5% estimated cost and `HIGH` complexity
  label. Root cause (verified, not guessed): `_estimate_codebase_context()`
  scans this repository's own source on every call and is nearly constant
  across calls in the same working directory; for a repo this size, that
  constant already consumes ~66% of the default `max_budget_tokens`
  (100,000), swamping any difference in prompt length. Recorded in
  `ARCHITECTURE_AUDIT.md` §7 and `ROADMAP.md` as a flagged follow-up, not
  silently patched — fixing it would change every existing estimate and
  needs its own deliberate design decision, not a side effect of this audit.
- **MAE/MAPE/precision/recall:** not computed. `goldenboy replay --json`,
  run for real against this machine's actual (empty) local history,
  reports `dataset_size: 0` — there is no historical outcome data to
  compute these against, exactly as `ROADMAP.md` already documented. No
  numbers were fabricated to fill this gap.

## 10. CI results

Not modified. `.github/workflows/ci.yml`'s existing jobs (lint, type check,
test+coverage across Python 3.9–3.13, package build+install smoke test,
`pip-audit`, and the `sdk-typescript` job) already cover everything this
audit added, since it added tests under `tests/` and `sdk/typescript/test/`
rather than new job configuration. One real gap this audit did surface and
did **not** fix: CI runs on `ubuntu-latest` only, while the CLI/SDK
subprocess contract is used cross-platform in practice — recorded in
`ARCHITECTURE_AUDIT.md` §8 and `ROADMAP.md` as Planned, not silently added
to CI without the user's sign-off on the added CI cost/runtime.

## 11. Remaining risks

1. **Estimator cost-estimate calibration** (§7) — real, reproducible,
   unfixed. The estimate is dominated by repo size, not task size, once a
   repo is moderately large.
2. **`HistoryStore.load_events()` has no size cap** — fine today, not
   provably fine forever; see `benchmarks/results/2026-09-15-scaling.md`.
3. **Protocol sync is still partly hand-maintained** — the new schema +
   tests catch drift in required fields and enum values, but the
   TypeScript enum lists in `schema.test.ts` are still a hand-copied
   mirror of `types.ts`, not derived from it automatically (TypeScript
   union types don't exist at runtime to introspect).
4. **CI is Ubuntu-only** (§10).
5. **1GB-scale history log behavior is genuinely unverified** — extrapolated
   from a linear trend up to 100MB, not measured.

## 12. What was intentionally NOT changed

- No Rust code, build step, or dependency was added anywhere.
- No second CLI implementation (TypeScript or otherwise) was built.
- No ML model, learned policy, or calibration change was made to
  `task_classifier.py` or `policies.py`.
- No ratio, threshold, or default in `GoldenBoyConfig`/`RiskEngine`/
  `Estimator` was changed — including the §7 finding, deliberately left
  as a recorded follow-up rather than an in-place fix.
- No server, database, or new IPC mechanism was introduced.
- No CI job, packaging config, or dependency (required or dev) was added
  to either `pyproject.toml` or `sdk/typescript/package.json` — the new
  JSON Schema checks use a purpose-built, dependency-free validator
  (`tests/schema_support.py`) instead of adding `jsonschema`/`ajv`.

## 13. Is Golden Boy ready for a production release?

**YES**, for what it actually claims to be: a small, deterministic,
zero-dependency budget/risk-decision library with a stable CLI, a
documented and now schema-checked protocol, and a thin cross-language
client — evidenced by 202/202 Python tests passing, 21/21 TypeScript tests
passing, clean lint/type-check on both sides, and this audit's fresh
benchmarks showing no operation is a bottleneck at any repository size the
project's own caps don't already bound.

**With one caveat, not a blocker:** the §7 finding means
`estimated_cost_percentage`/`complexity_label` should not yet be trusted as
a precise signal in a repository as large as, or larger than, this one —
they currently read as "large-ish repo" more than "this specific task."
This doesn't make the tool unsafe (the `RiskEngine`/budget-safety-margin
logic that actually gates STOP/CRITICAL decisions is unaffected — it still
correctly stops when usable budget is exhausted, per §7's own policy-
comparison table), but it does mean the *complexity/cost* half of a
`goldenboy analyze` decision is currently less informative than its
confident-looking number implies once the calling repo is mid-sized or
larger. Recommended before any release that leans on that number
specifically: address the §7 finding (either recalibrate
`max_budget_tokens`'s default or decouple its context-size term from
prompt-complexity weight) as its own deliberate change — not bundled into
this audit, which was scoped to measurement, not to changing existing
policy.
